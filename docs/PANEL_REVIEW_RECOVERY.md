# v1.10.1 · 로또 페이지 복구 및 이전 당첨 기록의 리뷰 이관

## 페이지가 사라지는 경로 수정

기존 패널 갱신은 페이지를 먼저 제거한 뒤 비동기로 다시 등록했습니다. 설정을 저장해 통합을 다시 불러오거나 데이터 갱신이 지연/실패하는 동안 메뉴가 없어질 수 있는 구조를 수정했습니다.

- 설정 재로드에서는 `/lotto-645` 페이지를 삭제하지 않습니다.
- 기존 패널을 동기적으로 교체하고 여러 통합 설정의 등록을 직렬화합니다.
- 외부 당첨 이력 수신보다 페이지를 먼저 등록합니다. 통합 재로드 중의 구매 저장은 거절하며 이전 데이터를 사용해 저장하지 않습니다.
- 패널이 등록된 뒤 경로만 빠진 경우, 기존 분 단위 작업에서 로컬 등록 상태를 확인해 복구합니다. 이 복구 자체는 외부 요청을 하지 않습니다.
- 정적 파일/웹소켓 핸들러는 HA 프로세스당 중복 등록하지 않습니다.
- 실제 통합 삭제나 사용 중지 시에만 해당 항목을 제거합니다. 다른 사용자 패널을 덮어쓰지 않습니다.
- 기기 정보의 설정 링크와 페이지의 `메뉴`, `통합·센서 보기` 링크를 추가했습니다.

페이지는 **추가 관리 화면**입니다. 기존 추천 센서, 대시보드, 자동화는 유지합니다. 구매정보 접근은 기존처럼 관리자에게만 허용합니다. 사용자가 사이드바를 직접 숨겼거나 비관리자로 로그인한 경우까지 권한을 바꾸거나 숨김 설정을 강제로 변경하지 않습니다.

업데이트 후 HA를 재시작하고 관리자 계정에서 `로또 복권` 메뉴 또는 `/lotto-645` 경로를 엽니다. 실제 운영 HA의 로그와 사이드바 개인 설정을 읽은 것은 아니므로 사용자 환경의 단일 원인을 확정했다는 뜻은 아닙니다.

## 5등 판정과 평가대기가 함께 나타나는 문제

이전 버전에서 `draw_evaluation`의 판정 결과는 남았으나 그 번호를 생성한 스냅샷이 다음 회차로 교체된 경우, 리뷰가 이 판정 기록을 가져오지 못했습니다. 보관된 실제 번호와 기준회차, 추첨 전 생성시각을 확인하는 이관 경로를 추가했습니다.

- 출처가 분석/AI이고 생성시각과 기준회차가 검증되면 실제 저장번호를 기존 ReviewBook 규칙으로 이관합니다.
- `evaluated_at`은 판정시각이지 생성시각이 아닙니다. 이를 출생/추천 생성시각처럼 사용하지 않습니다.
- AI 번호는 AI의 실제 생성시각이 있어야 하며 로컬 추천시각을 빌려 쓰지 않습니다.
- 구매번호는 추천 방식 리뷰에 섞지 않습니다.
- 판정 기록의 옛 등수나 당첨번호를 그대로 믿지 않고 확인된 이력으로 다시 계산합니다.
- 동일 회차는 재시작·반복조회 후에도 한 번만 집계하고 이미 고정된 추첨 전 번호를 사후 교체하지 않습니다.
- 생성시각/기준회차가 없거나 늦은 경우에는 별점을 만들어 넣지 않고 `n회 5등 · 누적평가 제외`와 이유를 표시합니다.

스크린샷의 본번호 `7,13,16,23,24,43`과 앙상블 `7,13,15,24,38,42`는 정확3개, ±1대응2개입니다. 기존 공개 리뷰식으로 57.1점(표시 반올림), 5등입니다. 누적 반영은 실제 저장기록의 추첨 전 생성 근거가 확인되는 경우에만 수행합니다. 과거 추천을 재생성해 성능을 꾸미지 않습니다.

## 모바일 화면

메뉴 열기 버튼·통합 바로가기, 안전영역 여백, 리뷰 표 가로 스크롤, 당첨 결과의 잘못된 글자 분할 방지를 적용했습니다. 구매번호를 편집하는 동안 결과 갱신이 입력값이나 저장 리비전을 덮어쓰지 않는 기존 동작을 유지합니다.

## 로고의 정확한 상태

페이지에는 원본 로고 전용 경로와 표시 영역을 연결했습니다. 설치된 `brand/logo.png`가 사용자가 제공한 원본 PNG 또는 로컬에서 RGBA 픽셀 동등성을 검증한 무손실 PNG 해시와 일치할 때만 표시합니다. 기존 작은 양자화 이미지를 원본인 것처럼 표시하지 않습니다.

**이번 코드 변경만으로 원본 바이너리가 저장소에 업로드됐다는 뜻은 아닙니다.** 실제 원본 PNG와 좌측만 크롭한 정사각 PNG의 원격 교체는 여전히 별도 미완료 항목입니다. 새로 그리기·팔레트 축소로 대신하지 않습니다. 이전에 제공한 정확한 브랜드 파일 패키지를 설치했다면 이 페이지 연결을 사용할 수 있습니다.

GitHub main 보호 또한 기존 연결의 Administration 권한 제한으로 미적용이며, 가져오기 JSON과 실제 서버 보호를 구별합니다. 보호 권한을 우회하지 않습니다.
